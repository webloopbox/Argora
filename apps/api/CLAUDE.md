# apps/api - Argora backend

NestJS application. Owns the database, the AI integrations, and every API contract (whose shapes are exported from `@argora/core`).

## Rules specific to the backend

- **Contracts live in `@argora/core`.** Every request/response DTO, every enum, and every shared interface must be imported from there. Do not define controller payload types locally - if something is missing, add it in `packages/core` first.
- **Validation:** use the DTOs from `@argora/core` as the single source of truth for `class-validator` decorators where possible. If a DTO needs runtime validation that doesn't belong in a shared package, wrap it in an API-side schema rather than duplicating the shape.
- **AI service must use a Strategy Pattern.** One interface (`LlmProvider`, four methods) with a concrete implementation per vendor in `src/ai/providers/`. Domain/service code depends on the interface, never on a concrete vendor SDK, and adding a vendor must not require touching callers. Implementations that exist today: `watsonx`, `together`, `gemini`, `claude`, `openai`. Only the first three are instantiated by `LlmRegistry`; wiring `claude` or `openai` in means editing the registry, not just supplying a key. `LlmRegistry` reads credentials from config and skips any vendor whose keys are absent, so an empty registry is a valid boot state - the app starts, the AI features are simply unavailable.
- **Embeddings are not part of `LlmProvider`.** `EmbeddingService` (`src/ai/embedding.service.ts`) owns a single active embedding vendor for the whole process, because vectors from different models are not comparable and duplicate detection compares stored vectors against fresh ones. Switching `EMBEDDING_PROVIDER` therefore invalidates every stored embedding and requires a re-embed pass (`scripts/reembed-existing.mjs`). The service returns `null` instead of throwing when a vendor call fails, and `checkDuplicate` turns that into "no similarity" so a broken embedding vendor never blocks a submission.
- **Prompt language follows the debate, and every prompt builder implements both languages.** `LlmProvider` inputs carry `lang: DebateLanguage`, taken from the `Debate` that `VisibilityGuard` attaches to the request - never from the request body, which a client could forge. Adding or editing anything in `src/ai/prompts/` means updating the Polish and English variants together; `synthesis.prompt.ts` keeps its strings in a `Record<DebateLanguage, SynthesisCopy>` precisely so a missing variant fails to compile instead of silently falling back. This matters beyond cosmetics: generated premises are persisted as graph nodes, and a mixed-language tree defeats the cosine-similarity duplicate check.
- **Provider failures must not surface raw.** Every call into an `LlmProvider` goes through `AiService.callProvider`, which funnels vendor errors into `upstreamAiException` (`src/ai/upstream-error.ts`): a throttle becomes 429, anything else becomes 503, both with a Polish message. This matters because watsonx enforces a low requests-per-second cap, so two AI actions fired back to back are enough to trip it. Never `await provider.x()` directly from a new code path, and never let an SDK message reach the response body - it is English and can leak endpoint or quota details. `checkArgumentSide` is the one deliberate exception: it already falls through to the next provider and degrades to "no mismatch" instead of failing the user's submission.
- **Per-endpoint throttling.** Each AI route owns one named `@Throttle` bucket (`ai-generate` 10/min, `ai-duplicate` 20/min, `ai-check-side` 20/min, `ai-synthesize` 5/min) and must `@SkipThrottle` the other three. `ThrottlerGuard` evaluates every bucket registered in `app.module.ts` on every guarded route, so omitting the skips silently makes the smallest limit the effective limit everywhere. `AiThrottlerGuard` keys the counter on the authenticated user id and falls back to the request IP.
- **Archiving is soft-delete, not hard-delete.** Every table that holds debate data (`users`, `debates`, `arguments`, `votes`, `groups`, `group_memberships`, `group_invitations`) has an `archivedOn: Date | null` column. "Deleting" a row means setting `archivedOn = now()`, never `DELETE FROM`. Reason: all data must remain available for later analysis, and hard-deletes destroy the history we rely on. Concretely:
  - Every find-options read goes through `activeWhere` (`src/common/repository/soft-delete.ts`). Its `ActiveWhere` return type keeps `archivedOn` required and operator-valued, so a filter it built cannot be weakened downstream. It does not force the call: a `find({ where: { … } })` written without it compiles and silently reads archived rows. Uniformity is what makes the omission visible in review, so write every read the same shape and never hand-roll `archivedOn: IsNull()` at a call site.
  - QueryBuilder aggregates cannot take that object, so they spell `archived_on IS NULL` out. Those are the places to check first when a count looks wrong.
  - Archiving stays in the services rather than in a generic helper, because every archive cascades to its child rows inside one transaction with the same timestamp.
  - Analytics and admin paths may opt in to reading archived rows explicitly.
- **Votes are soft-archived too, and there is at most one active vote per (argument, user).** That uniqueness is a partial unique index in `db/init.sql`, not a TypeORM `@Unique`, because it has to be scoped to `WHERE archived_on IS NULL`. Changing a vote's direction updates the existing row; retracting archives it, so a retract-then-vote sequence leaves two rows and only the active one counts.
- **Debate visibility has two modes and is an authorization boundary.**
  - **Public debates:** readable by anyone (including anonymous visitors). Writes (create debate, add argument, vote, etc.) require an authenticated user, but no further gating - any logged-in user may participate.
  - **Private group debates:** both reads and writes require membership in the owning group. Every endpoint returning group-debate data - even a single field - must enforce membership. Do not add "shortcut" endpoints that skip this check because the data seems harmless.
  - Visibility mode is set at debate creation and is load-bearing. `VisibilityGuard` is that single check - do not re-implement it per endpoint, and do not resolve the debate a second time inside a service. Routes scoped on an argument rather than a debate (voting, retracting a vote, archiving an argument) name their param `:argumentId` precisely so the guard can reach the debate through it.
  - The consistency of `visibility` with `groupId` is enforced twice on purpose: in `DebatesService.create` so the user gets a readable message, and by a check constraint on the table so no other write path can produce an inconsistent row.
- **Group invitations are system-internal and require invitee acceptance.** Model invitation and membership as two separate entities:
  - A group owner creates an **invitation** by searching the registered user directory and targeting an account id (never an email). No email flow, no invite tokens, no external signup links - the invitee must already exist in the system.
  - The invitation is **pending** until the invitee acts on it from their own panel. Acceptance promotes it to a **membership**; decline closes it. Only the invitee can accept or decline their own invitation - an owner cannot self-accept on behalf of a user.
  - Authorization reads group membership, **not** pending invitations. A user with only a pending invitation has no access to group data; endpoints enforcing group membership must check the membership table, not the invitation table.
  - Endpoints that add a membership accept a user id; endpoints that list a user's pending invitations are scoped to the caller.
